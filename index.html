Java Object Semantics

Most introductions to object-oriented programming stop at the vocabulary: a class is a blueprint, an object is an instance, inheritance means reuse. That vocabulary is not wrong, but it does not let you predict what a program does. This reference is about the semantics underneath — which method the JVM actually invokes, in what order fields acquire their values, why a HashSet can fail to find an element you just inserted, and why List<String> is not a subtype of List<Object>.

Every claim here is checkable against the Java Language Specification, and the section numbers are cited so you can check them. The interactive panels are not illustrations; they model the resolution rules directly, so working through them is a way of testing whether your mental model matches the language.

01

The object model: references, identity, and equality

A Java variable of a reference type does not contain an object. It contains a reference to an object, and the object itself lives on the heap. This single fact explains aliasing bugs, defensive copying, and the difference between == and equals. Every other topic in this document depends on it.

Assignment copies the reference. There is no implicit copying of objects anywhere in Java: not on assignment, not on argument passing, not on return. Java is strictly call-by-value, but for reference types the value being passed is the reference. A method therefore cannot reassign the caller's variable, yet it can freely mutate the object that variable points at.

Identity versus equality

== on reference types asks whether two references point at the same object. equals asks whether two objects are interchangeable for the purposes of the class that defines them. The default Object.equals implementation is identity comparison, so a class that does not override equals answers both questions the same way — which is why the distinction is easy to miss until it produces a bug.

Specification · JLS §15.21.3

For operands of reference type, == produces true if and only if both operands refer to the same object or both are null. The comparison is a well-defined operation on references and is never redirected to a user-defined method.

The trap worth committing to memory involves autoboxing. Integer.valueOf is required by the specification to return cached instances for values in the range −128 to 127, and is permitted but not required to cache other values. Identity comparison on boxed integers therefore has a result that depends on the magnitude of the number.

PuzzlePredict the output before revealing
true / false / true

Both literals assigned to Integer are autoboxed through Integer.valueOf. For 127 the specification mandates a cached instance, so a and b are the same object and == is true. For 128 the HotSpot default cache upper bound has been exceeded, so two distinct objects are allocated and == is false. equals compares the wrapped int values and is true in both cases.

The cache bound is tunable with -XX:AutoBoxCacheMax, which means the value of c == d is not fixed by the language at all. Code whose behaviour depends on it is broken by construction.

true / false / true

"hel" + "lo" is a constant expression: both operands are compile-time constants, so the compiler folds it to "hello" and the result is the interned pool instance. s1 == s2 is therefore true. Had either operand been a non-final variable, the concatenation would happen at runtime and allocate a fresh object.

new String(...) is an explicit allocation and always produces a distinct object, so s1 == s3 is false. intern() returns the pool's canonical instance for that character sequence, which is s1.

Working rule

Use == on reference types only when you genuinely mean identity — cycle detection, sentinel comparison, cache lookups keyed on instance, and enum constants, where identity and equality coincide by construction. In all other cases use equals, and reach for Objects.equals(a, b) when either operand may be null.

  2. 1.2 Construct two String references s and t such that s.equals(t) is true, s == t is false, and neither is created with new. State which language rule makes your construction work.

Initialization order and the partially built object

Object construction in Java is a fixed, specified sequence — not a single atomic event. Knowing the sequence lets you explain a family of bugs that otherwise look like the language misbehaving, most importantly the case where a final field is observed holding zero.

Specification · JLS §12.4, §12.5

Class initialization happens once, on first active use: static fields are given default values, then static initializers and static field initializers run in source order.

Instance creation proceeds: allocate and zero all instance fields; evaluate the constructor's arguments; delegate to this(...) if present, otherwise invoke the superclass constructor; then run instance initializers and instance field initializers in source order; finally run the remainder of the constructor body.

The consequence to internalize is that the superclass constructor runs to completion before any subclass field initializer runs. During the superclass constructor, the object already has its final runtime type, so virtual calls dispatch to subclass overrides — but those overrides see subclass fields still holding their default values.

TracerStep through new Circle(2.0)

A three-level hierarchy with static blocks, field initializers, instance initializer blocks, and constructor bodies. Step forward to see the exact order the JVM uses.

    Note two details the tracer makes concrete. All three static blocks run before any instance work, and they run top-down through the hierarchy because initializing a class requires its superclass to be initialized first. And within each level, field initializers and instance blocks interleave in source order — they are not two separate phases.

    Calling an overridable method from a constructor

    This is the canonical construction bug, and it defeats even final fields.

    PuzzleA final field observed as zero
    a Derived of size 0
    a Derived of size 42

    The Base constructor invokes describe(). Dispatch is on the runtime type, which is already Derived, so the override runs. But Derived's field initializers have not executed yet — the object is still in the zeroed state from allocation — so size reads as 0. The second call, after construction completes, sees 42.

    final does not help. final constrains how many times a field may be assigned, not when it becomes visible. A final field is readable in its default state for the whole window between allocation and its initializer running, and the compiler does not warn you.

    The fix is structural, not cosmetic: a constructor must not call any method that a subclass could override. Restrict constructors to private, static, or final methods, or move the work into a factory method that fully constructs the object before invoking anything on it.

    Pitfall

    A constructor that calls an overridable method publishes a partially initialized this to code it does not control. The same hazard appears whenever a constructor registers this with a listener, starts a thread, or stores this in a static registry: another thread or callback can observe the object before its invariants hold.

    Encapsulation as invariant protection

    Encapsulation is routinely taught as "make fields private and add getters and setters". That formulation is close to meaningless: a class with a private field, a getter, and a setter is exactly as mutable and exactly as unprotected as one with a public field, only more verbose. Encapsulation is the practice of maintaining a class invariant — a property that is true of every instance, at every moment a client can observe it.

    A Range with the invariant lo <= hi is a useful test case. Public fields cannot maintain it. Getters and setters cannot maintain it either, because a two-step mutation passes through an invalid intermediate state. What maintains it is a constructor that validates, and mutators that only ever move between valid states.

    Access modifiers, precisely

    The four access levels are frequently misordered in textbooks. protected is wider than package-private, not narrower: it grants package access and additionally grants subclass access from other packages.

    ModifierSame classSame packageSubclass, other packageAnywhere
    privateyesnonono
    (none) package-privateyesyesnono
    protectedyesyesyes†no
    publicyesyesyesyes

    † With a restriction (JLS §6.6.2): outside the declaring package, a subclass may access a protected instance member only through a reference whose type is that subclass or a subtype of it. A Sub cannot use its inherited protected access to reach into an arbitrary Super instance.

    Pitfall

    A protected member is part of your public API for every subclass, forever. It is a commitment as binding as a public method, but it is easy to add carelessly because it feels internal. Prefer private with a protected hook only where extension is an explicit design goal.

    Representation exposure

    Declaring a field private protects the reference, not the object it points to. If a constructor stores a caller's mutable object, or a getter hands out the internal one, the encapsulation is decorative: clients can mutate your state without calling any of your methods.

    Working rule

    Distinguish unmodifiable from immutable. Collections.unmodifiableList(xs) returns a view: it rejects mutation through the view but still reflects later changes to xs. List.copyOf(xs) takes a snapshot and is genuinely immutable. Only the second is safe to return from a getter when the source list is still reachable elsewhere.

    Records

    Records (Java 16+) make the common case declarative. A record gives you final fields, a canonical constructor, accessors, and consistent equals, hashCode and toString. They do not give you invariant checking or deep immutability for free — a compact constructor supplies the first, and defensive copying is still yours to write.

    Exercises

    1. 3.1 A Period class stores private final Date start, end with the invariant start <= end, validates in the constructor, and exposes both via getters. Show that the invariant can still be violated, and repair the class without changing its public signature.
    2. 3.2 Explain why an immutable class may cache its hashCode in a non-final field without synchronization, and what property of the computation makes the benign race benign.

    Inheritance and dynamic dispatch

    Two independent questions get conflated under the word "inheritance". Subtyping is a statement about types: a Circle may be used wherever a Shape is expected. Subclassing is a statement about implementation: Circle inherits Shape's members. Java's extends couples them; implements gives subtyping without inherited state. Much of good design consists of wanting the first and avoiding the second.

    Specification · JLS §8.4.8

    An instance method m in a subclass overrides a superclass method when it has the same name and the same erased parameter types. The overriding method must not reduce visibility, must have a return type that is the same or a subtype (covariant return, Java 5+), and must not declare broader checked exceptions. Same name with different parameter types is overloading, which is a distinct mechanism resolved at compile time.

    Member kindOverridableResolved onMechanism
    instance methodyesruntime typevirtual dispatch
    static methodnostatic typehiding
    private methodnostatic typenot inherited
    final methodnoruntime typedispatch, but fixed target
    fieldnostatic typehiding

    That last row is the one that surprises people. Fields are never polymorphic. A field access is bound at compile time using the static type of the expression, so an object can have two fields of the same name — one from each level — and which one you read depends on the type of the reference you read it through.

    PuzzleFields hide, methods override
    Derived / Derived
    Base / Derived

    The object really does contain two String fields named name. The compiler picks which one to read from the static type of the expression: through d (type Derived) it reads Derived.name; through b (type Base) it reads Base.name. No dispatch is involved — the field offset is fixed in the bytecode.

    who() behaves differently because it is a virtual call. Both expressions compile to an invokevirtual on the same method signature, and the JVM resolves the target from the object's actual class, which is Derived in both lines.

    Field hiding is almost never intentional. Treat a repeated field name in a subclass as a bug until proven otherwise.

    What the declared type controls

    It helps to separate two roles. The static type of an expression determines which members you are permitted to name and which overload is selected. The runtime type determines which override actually executes. The resolver below applies both rules to a small hierarchy.

    A subclass that overrides methods depends on the superclass's internal call graph, which is not part of its documented contract. HashSet.addAll happens to call add in the current implementation; a subclass that counts insertions by overriding both will double-count. A later release may change that call graph without breaking any published contract, and your subclass breaks. This is the concrete argument behind "favour composition over inheritance" (Chapter 07).

    05

    Overload resolution happens at compile time

    Overriding and overloading are unrelated mechanisms that share a syntax. Overriding is resolved by the JVM from the object's class. Overloading is resolved entirely by the compiler from the static types of the argument expressions, and the chosen signature is then fixed in the bytecode. A method call in Java is therefore resolved in two stages: the compiler picks the signature, and the JVM picks the body.

    Specification · JLS §15.12.2

    Applicable methods are sought in three phases, and the search stops at the first phase that finds any candidate:

    1. Phase 1 — strict invocation: subtyping and widening primitive conversion only. No boxing, no unboxing, no varargs.
    2. Phase 2 — loose invocation: boxing and unboxing now permitted. Still no varargs.
    3. Phase 3 — variable-arity invocation: varargs considered.

    Within the successful phase, the most specific applicable method wins; if no candidate is strictly more specific than all others, the call is ambiguous and does not compile.

    The three-phase rule has a consequence students consistently get wrong: a widening primitive conversion beats boxing, because it is available a whole phase earlier.

    PuzzleThree resolution traps
    Object / String / Object / String

    f(o) prints Object. The runtime class of o is String, but overload resolution never consults runtime types — the static type of o is Object, so only f(Object) is applicable. This is the crispest demonstration that overloading is not polymorphism.

    f("hello") prints String: both overloads are applicable, and String is more specific than Object. A cast changes the static type and therefore changes the answer.

    f(null) prints String. The null literal is assignable to both parameter types, so both are applicable, and the most-specific rule picks String. Add a third overload f(Integer) and the same call stops compiling: String and Integer are unrelated, neither is more specific, and the invocation is ambiguous.

    long

    Phase 1 permits widening primitive conversion, so g(long) is applicable immediately with int → long. Resolution stops there. g(Integer) would need boxing, which is phase 2; g(int...) is phase 3. Neither is ever considered.

    Delete g(long) and the answer becomes Integer, because phase 2 now succeeds. Delete that too and it becomes varargs. The phases are strictly ordered, and a candidate in an earlier phase always wins regardless of how much "closer" a later candidate looks.

    B.h(Object)

    Both stages are in play, in order. The compiler resolves the overload against the static type A, which declares only h(Object) — B.h(String) is invisible through an A reference, so the bytecode names the signature h(Object). Then the JVM dispatches that signature on the runtime type B and finds B's override.

    The result is a method in B, but not the one that looks like the better match. Changing the declared type of x to B changes the output to B.h(String) without touching the object.

    Working rule

    Overloads whose parameter types are related by subtyping, boxing, or arity are a standing hazard. Prefer distinct method names (fromString, fromInt) over overloads that differ only in a way the reader must run the three-phase algorithm to resolve. When you must overload, keep the arities different — a reader can resolve that by counting.

    Exercises

    1. 5.1 List.remove is overloaded as remove(int) and remove(Object). For List<Integer> xs, determine what xs.remove(1) does versus xs.remove(Integer.valueOf(1)), and name the phase that decides it.
    2. 5.2 Write three overloads such that adding a fourth, more specific overload changes the meaning of an existing call site without any error or warning. Explain why this makes overloading a source-compatibility hazard for library authors.

    Abstract classes and interfaces

    Since Java 8 gave interfaces default methods, the two mechanisms overlap substantially, and the old summary — "interfaces cannot have code" — is obsolete. The remaining distinction is sharp and worth stating exactly: an abstract class can hold state and you get only one; an interface cannot hold instance state and you can implement many.

    Abstract classInterface
    Instance fieldsyesno (constants only)
    Constructorsyesno
    How many per classonemany
    Method bodiesyesdefault, static, private
    Access levelsall fourpublic, or private helpers
    Can restrict implementorsvia constructor accessvia sealed

    Default methods and the diamond

    Multiple inheritance of behaviour reintroduces the conflict that Java originally avoided: if two interfaces supply a default method with the same signature, which one does the implementing class inherit? Java resolves this with three ordered rules rather than an arbitrary linearization.

    Specification · JLS §9.4.1
    1. Classes win. A concrete method inherited from a superclass takes precedence over any interface default.
    2. The most specific interface wins. If one candidate interface is a subinterface of the other, its default is chosen.
    3. Otherwise it is an error. With unrelated candidates the class must override the method; it may delegate explicitly with Interface.super.method().

    Note that Interface.super.method() is legal only for an interface the class directly implements. There is no way to reach a grandparent interface's default, which is a deliberate restriction: it keeps the resolution rules local and decidable.

    Two shapes for the same problem

    The choice between an abstract class and an interface usually shows up as a choice between two patterns. Template Method fixes the algorithm in a superclass and leaves holes; Strategy keeps the algorithm in a collaborator and injects it. They solve the same problem with opposite dependency structures.

    Working rule

    Reach for an interface by default: it permits multiple implementation, admits lambdas when it has a single abstract method, and does not spend the one inheritance slot. Choose an abstract class when subclasses must share state or a non-public constructor, and when you intend to control extension. If a type is meant to be extended, say so in its documentation and make the extension points explicit — every other method should be final or private.

    Sealed hierarchies

    Java 17's sealed lets a type enumerate its permitted subtypes. This converts an open hierarchy into a closed sum type, which in turn lets the compiler verify that a switch is exhaustive — so adding a variant produces a compile error at every site that must handle it, rather than a runtime surprise.

    This is worth contrasting with the classical object-oriented answer, which would put an abstract eval() on Expr and override it in each subtype. The two arrangements differ in what is cheap to change: the polymorphic version makes adding a variant easy and adding an operation invasive; the sealed-plus-switch version reverses that. This trade-off is the expression problem, and neither side of it is the wrong answer in general.

    Exercises

    1. 6.1 Give a case where rule 1 ("classes win") produces behaviour a reader would not predict: a class inherits a concrete method from its superclass that silently shadows a default the class appears to have opted into by implementing the interface.
    2. 6.2 Take the Expr hierarchy and add a Mul variant. List every compile error this produces in the sealed version, then do the same for a polymorphic version, and use the difference to state the expression problem in your own words.
    07

    Substitutability and variance

    The compiler enforces that a subclass has the right shape: matching signatures, compatible return types, no narrowed access. It cannot enforce that the subclass has compatible behaviour. That obligation is the Liskov Substitution Principle, and violating it produces code that compiles and type-checks while breaking callers who did nothing wrong.

    Definition · Liskov (1988)

    If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering any property that programs depend on. Concretely, an override may weaken preconditions (accept at least as much), must strengthen or preserve postconditions (promise at least as much), and must preserve every supertype invariant.

    The standard counterexample is Square extends Rectangle. Geometrically a square is a rectangle; as a mutable type it is not a subtype, because Rectangle's setters carry an implicit postcondition that Square cannot honour.

    The method check is correct against Rectangle's contract, and it fails when handed a Square. Nothing in the type system detected this. The resolutions are to make the type immutable (then withW returns a new object and the postcondition is expressible), or to drop the inheritance and let both implement a common read-only interface.

    Arrays are covariant; generics are not

    Java made arrays covariant in 1.0 — String[] is a subtype of Object[] — which is unsound, and the language pays for it with a runtime check on every array store. Generics, added later with full knowledge of that mistake, are invariant: List<String> is not a subtype of List<Object>. The wildcard syntax exists to recover the flexibility that invariance costs, without the unsoundness.

    ExplorerCompiles, fails to compile, or fails at runtime

    Select a row to see which rule decides it.

      Working rule · PECS

      Producer extends, Consumer super. If a parameter is a source you read T values out of, declare ? extends T. If it is a sink you write T values into, declare ? super T. If you do both, you cannot use a wildcard and must take an exact T. This is why the signature of Collections.copy is copy(List<? super T> dest, List<? extends T> src).

      Erasure

      Generics are a compile-time discipline. The compiler checks types, inserts casts, and then erases the type arguments; the bytecode for List<String> and List<Integer> is identical. Every generics restriction that feels arbitrary follows from this one implementation decision.

      RestrictionBecause erasure means…
      x instanceof List<String> is illegalthere is no runtime record of the type argument to test
      new T[n] and new List<String>[n] are illegalthe array's runtime store check could not be generated soundly
      new T() is illegalno constructor is known at the erased call site
      f(List<String>) and f(List<Integer>) cannot coexistboth erase to f(List) — a clash, not an overload
      a type parameter cannot be staticthe class has one runtime representation shared by all instantiations

      Composition over inheritance

      The fragile base class problem from Chapter 04, made concrete. The goal is a Set that counts attempted insertions.

      The composed version is longer, and that verbosity is the entire cost. In exchange it depends only on Set's published contract, works with any Set implementation passed in, and cannot be broken by a change to HashSet's internals. Inherit only when the subclass genuinely is a specialization of the superclass and the superclass was designed and documented for extension.

      Exercises

      08

      The Object contract

      Every class inherits equals, hashCode and toString from Object, along with obligations attached to them. These are not stylistic conventions: the collections framework is written against them, and a class that violates them produces data structures that lose elements with no exception thrown.

      Specification · java.lang.Object

      equals must be reflexive (x.equals(x)), symmetric (x.equals(y) == y.equals(x)), transitive, and consistent across repeated calls; x.equals(null) must be false.

      hashCode must return the same value on repeated calls, and equal objects must have equal hash codes. Unequal objects need not differ, but should, for performance.

      The two contracts are coupled in one direction only, and that asymmetry is where the bugs live. Overriding equals without hashCode leaves the inherited identity-based hash, so two equal objects land in different buckets and a hash-based collection never compares them.

      CheckerWhich collection behaviour breaks?

      Uncheck a clause to violate it, and see what the collections framework does in response.

      Why symmetry is hard under inheritance

      There are two ways to write the type test in equals, and both have a defect. instanceof accepts subclasses and therefore risks asymmetry; getClass() is symmetric but refuses to consider any subclass instance equal, which violates LSP for subclasses that add no state.

      Working rule

      There is no fully satisfying way to add a value component to an instantiable class and preserve both symmetry and substitutability — this is a real limitation, not a puzzle with a hidden answer. The practical resolutions: make value classes final (or use a record, which is implicitly final and generates a getClass-based equals); or favour composition, giving ColourPoint a Point field and an asPoint() view instead of extending it.

      compareTo and the sorted collections

      Comparable adds a further obligation that is easy to miss because most collections do not check it: compareTo should be consistent with equals, meaning x.compareTo(y) == 0 exactly when x.equals(y). Sorted collections use compareTo rather than equals for membership, so an inconsistent implementation makes TreeSet and HashSet disagree about the same elements.

      Why clone() should be avoided

      Cloneable is the standard library's clearest design mistake, and it is instructive because every defect follows from a principle covered earlier. The interface declares no methods, so it does not express a contract; Object.clone is protected, so implementing the interface does not make cloning available to callers; the default implementation copies fields without invoking a constructor, so class invariants are never established; and the copy is shallow, so mutable fields end up aliased between original and clone. A copy constructor or static factory has none of these problems.

      Exercises

      1. 8.1 Implement equals and hashCode for a Money(long minorUnits, Currency currency) value type. Then write a JUnit test that would actually fail if hashCode were omitted — note that a naive assertion on a.equals(b) passes regardless.
      2. 8.2 Build a HashMap<Key,String> where Key is mutable and is mutated after insertion. Show that the entry becomes unreachable through get while still being visible through entrySet(), and explain the mechanism in terms of bucket assignment.
      3. 8.3 ColourPoint above breaks symmetry. Rewrite it using composition so that no contract is violated, and state what capability the composed version loses relative to the inheriting version.
